# Задание 1. Проектирование API и базы данных каталога шаблонов

## Цель

Спроектировать небольшой сервис, который хранит шаблоны документов и историю их версий. На этом этапе нужен документ с вашим решением: модель данных, описание API и примеры запросов и ответов.

Писать backend, UI, миграции и парсер пока не нужно. Сначала обсудим проект, затем перейдём к реализации по частям. Устанавливать PostgreSQL и поднимать Docker для этого задания также не требуется.

## Что будет делать сервис

Пользователь готовит файл `.ott` или `.odt` в текстовом редакторе и загружает его в каталог. В файле могут быть текстовые поля вроде `{NAME}` и `{DATE}`.

Сервис должен позволять:

1. Загрузить новый шаблон.
2. Загрузить новую редакцию существующего шаблона, сохранив предыдущую.
3. Найти шаблон в каталоге.
4. Открыть его карточку и историю версий.
5. Получить описание и скачать файл конкретной версии.

Сравнение версий и веб-интерфейс появятся на следующих этапах. Сейчас их проектировать не требуется, но текст и поля каждой версии нужно предусмотреть в модели данных.

## Исходные правила

- У шаблона есть постоянный строковый идентификатор `template_id`, например `notice`. Он отличается от имени загруженного файла.
- У одного шаблона может быть несколько версий. Номер назначает сервис: `1.0`, `1.1`, `1.2` и так далее. В API это строка.
- Каждая успешная загрузка создаёт новую версию. Существующие версии не перезаписываются.
- Актуальная версия — последняя успешно сохранённая. После `1.9` идёт `1.10`.
- Для версии сохраняются название, комментарий к изменениям и метаданные файла на момент загрузки. В дальнейшем эти сведения не меняются.
- Допустимы `.ott` и `.odt`, максимальный размер — 20 МиБ.
- Метаданные и история хранятся в PostgreSQL. Байты файлов — в отдельном каталоге сервиса; в БД хранится ссылка на файл.
- Пользователей, авторизацию, удаление и редактирование сохранённых версий сейчас не проектируем.

Парсер предоставляется готовым файлом `template_parser.py`. На вход он получает байты файла и его имя, на выходе даёт текст, список полей, SHA-256, размер и формат. Формат страницы и ориентация передаются ему из формы. Изучать XML и реализовывать разбор не требуется.

## Часть 1. Спроектируйте БД

Определите, какие сущности нужны для перечисленных сценариев и как они связаны. Не начинайте с большого количества таблиц: у каждой должна быть понятная задача.

Для каждой таблицы опишите:

- название и назначение;
- поля, типы PostgreSQL и обязательность заполнения;
- первичный ключ — по чему однозначно находится запись;
- внешние ключи — как запись связана с другими таблицами;
- ограничения уникальности — какие значения не могут повторяться;
- индексы, которые нужны для ваших запросов, и зачем они нужны.

Предусмотрите хранение следующих сведений:

| Сведения | Что нужно решить |
|---|---|
| Идентификатор шаблона и время его создания | Где хранится постоянная информация о шаблоне |
| Номер версии, время загрузки, название и комментарий | Где хранится история изменений |
| Исходное имя, формат, размер и SHA-256 файла | Как описывается загруженный файл |
| Ключ или относительный путь файла | Как запись в БД связана с байтами на диске |
| Формат страницы и ориентация | Как сохраняются параметры конкретной версии |
| Извлечённый текст и список полей | Где сохраняется результат готового парсера |

Нарисуйте ER-диаграмму: таблицы, ключи и связи между ними. Можно использовать Mermaid или любой редактор схем. Готовая SQL-схема не требуется.

Коротко объясните три решения: как определяется актуальная версия; как исключается повтор одного номера у одного шаблона; где хранится список полей — в отдельной таблице или в JSONB. Единственного правильного варианта нет, но он должен соответствовать вашим сценариям.

## Часть 2. Спроектируйте REST API

Используйте следующие пути. Общий префикс — `/api/v1`.

| Метод и путь | Сценарий |
|---|---|
| `POST /templates` | Загрузить первый файл или новую версию существующего шаблона |
| `GET /templates` | Получить каталог с поиском и пагинацией |
| `GET /templates/{template_id}` | Получить карточку с историей и описанием актуальной версии |
| `GET /templates/{template_id}/versions/{version}` | Получить описание конкретной версии |
| `GET /templates/{template_id}/versions/{version}/file` | Скачать файл этой версии |

Для каждой ручки опишите:

1. Какие параметры приходят в пути, query string или теле запроса.
2. Какие поля обязательны, их типы и ограничения.
3. Что возвращается при успехе: HTTP-статус и пример тела ответа.
4. Какие ошибки возможны: HTTP-статус и пример сообщения.
5. Какие данные сервис читает или создаёт в вашей модели БД.

При загрузке используется `multipart/form-data`: `template_id`, `file`, необязательные `title`, `change_note`, `page_format` и `orientation`. Номер версии задаёт сервер. Формат страницы по умолчанию — `A4`, ориентация — `portrait`.

Для каталога предусмотрите `q`, `limit` и `offset`: поиск по идентификатору или названию, размер страницы и смещение. Поиск не учитывает регистр. В ответе нужны `total` и `items`; `total` считается до пагинации.

Используйте следующие имена:

| Ответ | Основные поля |
|---|---|
| Элемент каталога | `template_id`, `title`, `latest_version`, `versions_count`, `updated_at` |
| Карточка | `template_id`, `title`, `latest_version`, `versions`, `descriptor` |
| Описание версии | `template_id`, `version`, `title`, `kind`, `created_at`, `source_format`, `checksum`, `size_bytes`, `page`, `fields`, `change_note` |
| Успешная загрузка | Сведения о принятой версии и `saved: true` |

`descriptor` — описание актуальной версии, `kind` в нашем задании всегда `simple`. `page` содержит `format` и `orientation`. Элемент `fields` имеет вид `{"name":"NAME","type":"text","required":true}`. Остальные типы и вложенные структуры распишите сами. Даты возвращаются в UTC в ISO 8601.

При скачивании возвращается файл, а не JSON. Укажите его Content-Type и как клиент узнает имя скачиваемого файла.

Ожидаемые статусы: `201` для успешной загрузки, `200` для чтения, `400` для нечитаемого файла, `404` для отсутствующего шаблона или версии, `413` для превышения размера, `422` для неверных параметров. Конфликт одновременного создания версии допустимо описать через `409`; сложный механизм его разрешения сейчас не нужен.

На первом этапе достаточно Markdown с примерами JSON. Полный OpenAPI-файл, отдельная ручка сравнения, `dry_run` и пробная генерация пока не требуются.

## Часть 3. Проверьте проект на примерах

Пройдите эти ситуации на бумаге. Для каждой покажите запрос, результат и какие записи появились или были прочитаны в БД. Реальные SQL-запросы писать не нужно.

1. Загружен `Уведомление.ott` с `template_id=notice`: создана версия `1.0`.
2. Под тем же идентификатором загружен исправленный файл: создана `1.1`, версия `1.0` доступна для скачивания.
3. Файл с тем же именем загружен под другим `template_id`: это отдельный шаблон.
4. Запрошена версия, которой нет: получен `404`.
5. Парсер отклонил файл: успешная версия не создаётся, предыдущая актуальная версия остаётся доступна.

## Что сдать

Один файл `design.md`, который содержит:

1. Краткое описание сервиса своими словами.
2. ER-диаграмму и описание таблиц с типами, ключами и ограничениями.
3. Описание пяти ручек с примерами запросов, успешных ответов и ошибок.
4. Разбор пяти ситуаций выше.
5. Короткое обоснование решений и список вопросов, которые хотите обсудить.

Если диаграмма сделана картинкой, приложите её рядом с документом. Структуру самого `design.md` выберите удобную для чтения.

## Как будем принимать

- По документу понятно, как связаны шаблон, версия и сохранённый файл.
- История не теряется при новой загрузке, а номер версии не используется повторно у того же шаблона.
- Ответы API можно получить из предложенной модели БД; примеры не противоречат друг другу.
- Ошибки описаны, а отличия идентификатора шаблона, номера версии, имени файла и SHA-256 понятны.
- Вы можете объяснить выбор таблиц, ключей, типов и HTTP-статусов.

Можно пользоваться документацией и AI для обсуждения вариантов. Решение нужно проверить самостоятельно и уметь объяснить. После обсуждения зафиксируем проект и перейдем к следующему этапу — реализацию бека
